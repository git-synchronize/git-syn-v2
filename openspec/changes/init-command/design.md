## Context

Git SYN is modeled after the Git LFS extension. `git syn install` follows the same pattern as `git lfs install`: install a `pre-push` git hook into the target repository and register remotes in `.git/config`. The two core goals are:

1. **Configure the `pre-push` hook** — write an embedded hook script into `.git/hooks/pre-push` with `0700` permissions
2. **Populate `.git/config` from `.gitremotes`** — write remotes to `.gitremotes`, then read it back and register each entry in `.git/config`

Git SYN's purpose is remote repository synchronization for disaster recovery and censorship resistance. The `.gitremotes` file captures configured remotes so they can be registered in `.git/config` and kept in sync across multiple git forges.

`cmd/init.go` was generated by cobra CLI scaffolding. The command body opens the current directory via `go-git`, iterates remotes, and writes a `.gitremotes` file — but has stock placeholder text, no hook installation, no UX output, and no path flexibility.

## Goals / Non-Goals

**Goals:**
- Rename command to `install` (matching `git syn install` invocation and README)
- Accurate, user-facing help text describing the synchronization purpose
- Embed `pre-push` hook content as a Go string constant
- Write the hook into `.git/hooks/pre-push` and set `0700`
- Write `.gitremotes` from HTTPS/OpenSSH remotes; append entries to `.git/config`
- `--path` flag to target a repo other than `$CWD`
- Print `Updated git hooks. Git SYN initialized.` on success

**Non-Goals:**
- Changing the `.gitremotes` file format
- Interactive remote-editing or prompts
- Any changes to other commands

## Decisions

**Command name: `install` not `init`**
The README shows `install` as the command name, matching the Git LFS pattern (`git lfs install`).

**Function decomposition: `init_repo`, `install_hook`, `write_hook`, `set_file_permissions`**
The command `Run` body delegates to four functions:
- `init_repo(path string)` — opens the git repo, writes `.gitremotes` from filtered remotes, appends entries to `.git/config`
- `install_hook(hookType, hooksDir string)` — formats the embedded template for `hookType`, calls `write_hook` then `set_file_permissions`
- `write_hook(path, content string)` — writes hook content to disk via `os.WriteFile`
- `set_file_permissions(path string, mode os.FileMode)` — calls `os.Chmod`; separated so permission policy is explicit

**Hook content is an embedded Go string constant, not a file**
A single `hookContent` constant uses a `{{Command}}` placeholder, matching the Git LFS `hookBaseContent` pattern in `lfs/hook.go`. At install time `install_hook` replaces `{{Command}}` with the hook type name and passes the result to `write_hook`. The binary is self-contained with no runtime dependency on external files.

**Hook calls `git syn {{Command}}`, checks `git-syn` in PATH**
The hook uses `command -v git-syn` to test availability (matching Git LFS's `command -v git-lfs`), then delegates to `git syn {{Command}} "$@"`. `git-syn` is the binary name; `git syn` is how git invokes it as a subcommand.

**Hook permissions: `0700`, not `0755` as in Git LFS**
Git LFS uses `0755`. Git SYN uses `0700` (owner read/write/execute only) for least privilege: git invokes hooks as the same user who ran the git command, so owner-execute is sufficient.

**Append .gitremotes to .git/config using go-git's config API**
After writing `.gitremotes`, `init_repo` reads it back and registers each remote via `go-git`'s `repo.Config()` / `config.Remotes` map, then calls `repo.SetConfig()`. Deduplication is handled naturally — existing remote names are left unchanged. Raw file appending rejected — fragile and bypasses gitconfig encoding rules.

**Supported remote URL types: HTTPS and OpenSSH only**
Only `https://` and `git@` (OpenSSH SCP syntax) URLs are written to `.gitremotes`. Others are skipped with a warning. These cover the two dominant auth patterns for the multi-forge synchronization use case.

**Use `os.Getwd()` default with optional `--path` override**
A `--path` string flag defaults to `""`. When empty, fall back to `os.Getwd()`.

**Keep `log.Fatal` for errors**
Consistent with the existing file; switching error handling style is out of scope.

## Risks / Trade-offs

- Hook write may fail if `.git/hooks/` does not exist or is not writable → surfaced via `log.Fatal`
- No tests exist for this command → out of scope; existing manual smoke-test approach is unchanged

## Migration Plan

- Command rename from `init` to `install` is a breaking change for users calling `git syn init` directly → document in release notes
- No other config file or workflow impact
